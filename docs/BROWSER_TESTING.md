# Браузерные проверки ППР Контроль

Playwright запускает приложение с настоящим HTTP-сервером и проверяет действия пользователя в браузере. Конфигурация находится в [playwright.config.js](../playwright.config.js), сценарии — в [e2e](../e2e). Для каждого теста создаются отдельные данные, сервер и браузерный контекст. Вход выполняется через форму с настоящей серверной проверкой пароля: сервер работает в режиме `NODE_ENV=production`.

Браузер подключается через локальный HTTPS-прокси, который передаёт HTTP, SSE и WebSocket настоящему серверу приложения. Это сохраняет проверку защищённой cookie, как при размещении за HTTPS-прокси. Одноразовый сертификат создаётся в памяти; исключение проверки сертификата действует только в тестовом браузере. Настройки рабочего приложения и системное хранилище сертификатов не меняются.

## Локальный запуск

Команды выполняются из корня репозитория. В CI используется Node.js 22; его же следует использовать для воспроизводимого локального запуска.

```sh
npm ci
npx playwright install chromium webkit
npm run test:e2e
```

На Linux браузерам могут потребоваться системные библиотеки. Установка, которую использует CI:

```sh
npx playwright install --with-deps chromium webkit
```

`npm run test:e2e` сначала собирает `app.min.js` и `styles.min.css`, затем запускает браузерные сценарии. Запускать его удобно в отдельной рабочей копии. Обычная команда `npm test` продолжает запускать Node-тесты отдельно.

Профили браузеров:

| Профиль | Движок и параметры |
| --- | --- |
| `desktop-chromium` | Chromium, окно 1440 × 1000 |
| `android-chromium` | Chromium с эмуляцией Pixel 7 |
| `iphone-webkit` | WebKit с эмуляцией iPhone 13 |

Один профиль можно выбрать так:

```sh
npm run test:e2e -- --project=iphone-webkit
```

Мобильные профили проверяют поведение браузерных движков с заданными размерами экрана, touch-параметрами и user agent. Это эмуляция, а не запуск на физических Android/iPhone. Она не подтверждает работу установленной PWA, системных окон печати, реальной камеры или обмена файлами средствами конкретного телефона.

## Что проверяется

| Сценарий | Проверяемое поведение |
| --- | --- |
| Вход | Неверный пароль показывает ошибку; его можно исправить в той же форме; сессия восстанавливается после перезагрузки страницы при наличии сети. |
| Доступ и мобильные элементы | Оператор видит назначенный цех, чужое оборудование отсутствует, директорская кнопка скрыта; основные кнопки, напоминания и мобильная навигация доступны. Проверки видимости интерфейса дополняют серверные тесты прав доступа. |
| Печать журнала | Кнопка открывает настоящий popup с журналом выбранного оборудования. Проверяются таблица, завершённый ремонт, исполнитель, подтверждающий и отсутствие чужого оборудования; сохраняется снимок окна. Физическая печать и итоговый PDF этим сценарием не проверяются. |
| Обновление между пользователями | Оператор создаёт замечание через QR-диалог. Инженер в другом браузерном контексте видит его без перезагрузки; после последующей перезагрузки замечание остаётся сохранённым. |
| Очередь без сети | В открытом приложении отключается сеть, отметка QR сохраняется в локальную очередь и после восстановления связи отправляется на сервер один раз. Состояние очереди и сохранённая серверная отметка проверяются дополнительно к действиям в UI. |
| QR из изображения | Браузерный отказ `getUserMedia` моделируется через `NotAllowedError`. Пользователь повторяет попытку камеры и выбирает PNG через настоящий `filechooser`; изображение создаётся из тестового QR, проходит штатный декодер, открывает нужный узел и сохраняет результат обхода. Видеопоток физической камеры не используется. |

Автоматическая fixture также проверяет необработанные JavaScript-ошибки страницы. Ни успешный тест видимости, ни отсутствие таких ошибок не заменяют ручную проверку всех экранов приложения.

## Известная ошибка BROWSER-001

Сценарий `offline reopening preserves an authenticated worker session @known-issue` проверяет повторное открытие уже загруженной PWA без сети. После подготовки service worker и его кеша тест отключает сеть и перезагружает страницу. Желаемое поведение — сохранить профиль сотрудника и оставить окно входа скрытым.

Сейчас ошибка сети при `restoreServerSession` очищает сохранённый профиль, и окно входа появляется. В [realtime-and-offline.spec.js](../e2e/realtime-and-offline.spec.js) перед проверкой этого поведения установлен `test.fail` с идентификатором `BROWSER-001`.

Это **ожидаемый провал, а не успешно работающий сценарий**. Playwright учитывает ожидаемую ошибку отдельно и допускает успешный итог запуска, пока тест падает ожидаемым образом. Подготовка кеша и загрузка страницы выполняются до аннотации: ошибки этих этапов не должны маскироваться под BROWSER-001. После исправления поведения неожиданный проход сделает запуск неуспешным; тогда нужно удалить `test.fail`, сохранив проверку скрытого окна входа. При разборе отчёта необходимо проверять причину падения, а не только общий статус запуска.

На Windows вариант этого сценария для WebKit явно пропускается: `page.reload` без сети выдаёт внутреннюю ошибку движка ещё до проверки ППР. Это воспроизведено отдельно от приложения на минимальной странице с service worker, подтверждёнными controller и кешем, как по HTTP, так и по HTTPS. Пропуск не означает успех; на Linux сценарий остаётся включённым. Поведение физического iPhone нужно проверять отдельно.

## Наблюдение BROWSER-002 в Windows WebKit

В одном из прогонов очередь QR доставила отметку на сервер, но WebKit сообщил необработанную ошибку запроса `/api/state` с текстом `due to access control checks`. Причина пока не установлена; в минимальном примере вне ППР эта конкретная ошибка не повторилась.

Тест выделяет только этот точный текст, только на Windows WebKit и только после успешной проверки доставки без дублей. Такой результат отмечается как воспроизведённая известная ошибка. Любая другая или дополнительная ошибка остаётся неожиданным провалом. Если ошибка не возникает, сценарий проходит обычным образом. Это наблюдение стенда не доказывает такую же ошибку на физическом iPhone.

## Хранилища и изоляция

По умолчанию используется JSON во временном каталоге. [isolated-env.js](../tools/testing/isolated-env.js) очищает `DATABASE_URL`, `NEON_DATABASE_URL`, `SUPABASE_DATABASE_URL`, TLS-файлы и пароли; тест задаёт собственные порты и `DATA_DIR`. Пустые значения также препятствуют восстановлению рабочих URL и сертификатов из `.env`. Тестовые процессы останавливаются, временные каталоги удаляются после завершения сценария.

Для PostgreSQL предусмотрен отдельный профиль через `PPR_E2E_POSTGRES_URL`. [postgres-sandbox.js](../tools/testing/postgres-sandbox.js) принимает только пользователя `ppr_e2e`, локальный адрес `127.0.0.1`, `localhost` или `[::1]` и служебную базу `/postgres`, без параметров запроса. Для каждого теста helper создаёт новую базу со случайным именем `ppr_e2e_…`; после остановки приложения удаляет именно её. Fixture подставляет URL этой базы только после очистки трёх прикладных URL и требует фактического запуска PostgreSQL-хранилища, без тихого перехода на JSON.

На машине первоначальной локальной проверки настоящий PostgreSQL не установлен. Этот профиль подготовлен для CI; его работа с реальным PostgreSQL пока не подтверждена локальным запуском.

При наличии Docker можно отдельно подготовить одноразовый PostgreSQL 16. Следующая команда занимает локальный порт 5432 и использует только тестовые учётные данные:

```sh
docker run --rm --detach --name ppr-e2e-postgres --publish 127.0.0.1:5432:5432 --env POSTGRES_USER=ppr_e2e --env POSTGRES_PASSWORD=ppr-e2e-only --env POSTGRES_DB=postgres postgres:16
docker exec ppr-e2e-postgres pg_isready -U ppr_e2e -d postgres
```

Дождитесь ответа `accepting connections` от второй команды. Затем запустите тесты в PowerShell:

```powershell
$env:PPR_E2E_POSTGRES_URL = 'postgres://ppr_e2e:ppr-e2e-only@127.0.0.1:5432/postgres'
try {
  npm run test:e2e
} finally {
  Remove-Item Env:PPR_E2E_POSTGRES_URL -ErrorAction SilentlyContinue
}
docker stop ppr-e2e-postgres
```

Либо в bash:

```sh
PPR_E2E_POSTGRES_URL='postgres://ppr_e2e:ppr-e2e-only@127.0.0.1:5432/postgres' npm run test:e2e
docker stop ppr-e2e-postgres
```

Эта инструкция описывает подготовленный способ запуска, а не уже выполненную проверку PostgreSQL. Учётная запись `ppr_e2e` должна принадлежать отдельному тестовому экземпляру PostgreSQL и иметь права создавать и удалять тестовые базы.

## CI и отчёты

[browser-tests.yml](../.github/workflows/browser-tests.yml) запускается на pull request и push в `main`. Матрица `json` / `postgres` выполняется на Ubuntu с Node.js 22. Оба задания выполняют `npm ci`, установку Chromium/WebKit с системными зависимостями и `npm run test:e2e`. PostgreSQL 16 поднимается как одноразовый service только для варианта `postgres`; `PPR_E2E_POSTGRES_URL` задан только на соответствующем шаге тестов. Условное отключение service через пустое имя образа поддерживается [синтаксисом GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservicesservice_idimage).

После каждого задания шаг с `if: always()` загружает `playwright-report/` и `test-results/` в артефакт `browser-tests-json` или `browser-tests-postgres`. Срок хранения — семь дней. Если ошибка произошла до создания отчётов, шаг предупреждает об их отсутствии.

Открыть локальный HTML-отчёт:

```sh
npm run test:e2e:report
```

`test-results/results.json` содержит полный машиночитаемый результат. Отдельный `test-results/browser-summary.json` и строка `Browser behavior` разделяют успешные сценарии, воспроизведённые известные ошибки, пропуски и неожиданные результаты: стандартные итоги Playwright могут включать ожидаемые провалы в число passed.

Reporter признаёт известной только одну ошибку с маркером BROWSER-001 или BROWSER-002. Посторонняя ошибка, в том числе при очистке теста, переводит итог в failed. Это поведение проверяется отдельными Node-тестами. При ошибках сохраняются trace, снимок страницы, видео и журнал изолированного сервера; печатный сценарий дополнительно прикладывает снимок popup. Каталоги отчётов исключены из Git.
