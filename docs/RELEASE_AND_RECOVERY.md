# Публикация и восстановление

Рабочий сервис: `ppr-control ramazan` на Render, ветка `main` репозитория
`hofmankz100-bot/ppr-control`. Исходный коммит этого этапа — `5881501`.

## Перед обновлением

1. Проверить сборку, Node-тесты, браузерные сценарии JSON и PostgreSQL в CI.
2. Проверить тесты реальной PostgreSQL: две независимые сессии, конкурентные
   изменения, повторное подключение, rollback и ошибка непосредственно при COMMIT.
3. Проверить чистоту изменений каталога: имена узлов, постоянные QR, пользователи
   и производственные записи не должны меняться как тестовые данные.
4. Зафиксировать успешный рабочий коммит и состояние публичной диагностики.

## Первое обновление протокола записи

Старые серверы сохраняли `full_state` асинхронно. Новая версия использует
транзакцию и ревизию; блокировка берётся на время операции, поэтому два новых
экземпляра могут сменять друг друга при обычном обновлении.

Первый переход требует закрыть публичные изменения на время совместной работы
старого и нового кода. Render предоставляет для этого Maintenance Mode:
он возвращает пользователям HTTP 503, оставляя процесс работающим.
См. [документацию Render](https://render.com/docs/maintenance-mode).

Включение обслуживания выполняется непосредственно перед публикацией проверенной
версии. После успешного старта нужно дождаться завершения старого экземпляра,
выключить обслуживание и проверить доступность приложения, версию и хранилище.
Обслуживание не заменяет защиту БД от старых фоновых записей.

При первом старте сравниваются даты всех доступных legacy-копий. Защита
зеркал включается до чтения снимков; ошибки её установки не игнорируются.
После перехода отсутствующий `full_state` требует явного восстановления,
а не загрузки старого локального файла.

Neon недоступен с ошибкой превышения лимита передачи данных. Для первого

оно относится только к недоступной копии с этим именем, фиксируется в

Если Neon доступен, его содержимое всё равно проверяется. Перед самой
выкладкой снимки и постоянные QR следует проверить повторно.

Сборка сервиса должна использовать `npm ci && npm run build`; рабочий процесс
запускается командой `node server.js`. Публиковать следует только коммит
с успешными Node-проверками и обоими заданиями браузерной матрицы.

### Порядок восстановления

Возврат интерфейса и доменной логики следует выполнять с сохранением нового
протокола записи. Старая версия сервера, которая не увеличивает `state_revision`,
несовместима с защитой от устаревших записей. Обычная кнопка возврата к `5881501`
после включения этой защиты не является полноценным планом восстановления.

Предпочтительный порядок — оставить транзакционный слой и откатить отдельный
проблемный этап кода. Данные не откатываются вместе с программой.

Если требуется возврат всего старого сервера или смена основной базы:

1. Включить обслуживание и остановить все процессы, способные писать состояние.
2. Сохранить актуальное состояние основной БД и проверить резервные копии,
   номера ревизий, даты и наличие последних подтверждённых работ.
3. Подготовить совместимый сервер или явную обратную миграцию защиты БД.
   Не отключать защиту при одновременно работающих старых и новых экземплярах.
4. Запустить выбранную версию и проверить чтение и запись на выделенной тестовой
   среде; затем восстановить публичный доступ.

Зеркала помогают восстановлению, но не подтверждают отсутствие потери последних
данных сами по себе. Выбирать копию только по доступности сервера нельзя.
